## 1. 0:00–0:30｜题目与一句话方案

**画面**：赛题标题 + 一张状态机图（可从 `docs/04` 截）。

**旁白**：

> 赛题要求在漂移的工业数据流上，让模型自己发现漂移、决定要不要更新、验证、必要时回滚。
> 我们的做法是：平台每轮给父检查点和当前阶段公开数据，Harness 在父检查点上续训，
> 用同一个验证集比较，只有确实更好才提交，否则保持父模型。全程无人干预、断网可跑。

## 2. 0:30–1:20｜系统怎么跑一轮

**画面**：终端执行：

```bash
python scripts/test_harness_local.py --dataset A --rounds 2 --grow
```

**字幕/旁白**（指着滚动日志）：

> `describe` 先声明支持分类和回归；然后假宿主发来第 1 轮 start 帧。
> 看这几行：`rows=178 psi_prev=0.000 stage_changed=True rule=first_round`
> ——首轮做一次真实续训，5 个 epoch。
> 第二轮 `rule=new_stage`，因为训练数据从 178 行长到 445 行；`budget=2ep`。
> 每轮结束都有 `finish` 的 reason：历史、漂移、模型裁决、前后指标，一行能审计。

**画面**：打开 `%TEMP%\harness-local-A-*\workspace\state-round-2\harness_state.json`（或让脚本打印），
指出 `best/last/last_gain/stalled/profile/decisions`。

> 状态不是只存权重：还存了参考分布、上轮收益、连续无收益次数、最近 10 轮决策。
> 下一轮先用 `rnd.history()` 读平台历史，再决定预算——这就是“读历史—做实验—依据结果决策”。

## 3. 1:20–2:20｜v1 真实试运行：三个问题和四个修复

**画面**：平台 `#runs` 页，点开 2026-11-21 的 completed run；右侧放技术报告第 3 节。

**旁白**：

> 这是 v1 在平台上的真实试运行：A/B/C 各 10 轮，全部 finish。
> A 的 macro-F1 是 0.8735，B 的 MAE 506.7 分钟，C 的 MAE 41.1 循环。
> 但报告暴露了四个问题：
> 第一，回归的 best 初值是 0，而 RMSE 越低越好，于是 B/C 每轮都像掉了 600 分；
> 第二，Qwen3.5 的回复在 reasoning_content 里，我们只读了 content，所以每轮 reason 都是“no model text”；
> 第三，C 第 4 到第 10 轮候选全被拒，但每轮还在花 4 个 epoch；
> 第四，漂移是拿“当前训练 vs 当前验证”算的，不能区分新阶段和同一批数据。

**画面**：切到 `src/harness/round_controller.py` 的 `choose_budget` 表，快速高亮
`first_round / new_stage / stalled / calibration`。

## 4. 2:20–3:20｜v2 回放：少花 47% 的训练

**画面**：终端：

```bash
python scripts/replay_trial.py
```

输出 119 → 63 epochs，省 56 个；然后打开 `reports/v2_replay_v1.md` 的汇总表和 B/C 逐轮表。

**旁白**：

> 把 v1 报告里每轮的阶段、PSI、前后指标原样喂给 v2 的预算函数，不重新训练，
> 看同样信号下 v2 会怎么花：119 个 epoch 降到 63 个，少 47%，估计少 1291 CPU 秒。
> A 一个 epoch 都没省，因为它的每次更新基本都有正收益；省下来的主要是 B/C
> 那些“候选已经被拒还继续重训”的轮次。
> 这是反事实回放，不是新实验；v2 的真实成绩要等下一次试运行。

**画面**：滚动 B/C 表，指出第 4 轮以后 `v2_epochs=0`、`rule=stalled`。

**画面**：终端：


**旁白**：

## v4/v5 版分镜（2026-11-24，推荐用这版）

### 0:00–0:25｜题目与策略

**画面**：赛题标题 + 一句话状态机。

**旁白**：我们在漂移数据流上做受控续训。v2 已经把 B 的 MAE/RMSE 减半、墙钟减半；
这一轮冻结 A/B，只改 C：先撤销一个被实测证伪的 145 上限，再做工况校准。

### 0:25–1:10｜v4：撤销上限 + 三项工程修复

**画面**：

```bash
git log --oneline -3
python -m unittest discover -s tests -q
```

**旁白**：v3 把 C 的预测硬压到 145，A/B 与 v2 逐位相同，C 反而全面变差：
MAE 41.12→43.79，RMSE 56.38→62.88，NASA 8.85×10¹⁰→2.44×10¹²。
原因不是“上限不够大”，而是 C 的 RUL 真值最大 542、公开验证集 33% 的样本 >145。
v4 直接移除上限，并修三项工程问题：特征路径缓存、历史增益口径、连续失败熔断。

### 1:10–2:00｜C 公开验证对照

**画面**：打开 `reports/本地审计_2026-11-24.md` 的表。

**旁白**：同一个第 3 轮模型、同一批 23,049 条公开验证样本：
v4 无上限 MAE 37.856、RMSE 51.691、NASA 4.321×10⁹；
v5 工况校准 ±10 后 MAE 36.536、RMSE 50.049、NASA 2.378×10⁹。
相对 v4：RMSE -3.18%，NASA -44.97%。

### 2:00–3:00｜v5 校准怎么做的

**画面**：打开 `vendor/contest_baselines/c_calibration.py`，高亮
`_conditions`、`fit`、`np.clip(correction, -10, 10)`。

**旁白**：只用公开训练集，按第一项运行设置分工况；在工况内估计传感器均值和方差，
用分段线性函数拟合父模型残差；每个样本最多修正 ±10；没见过的工况沿用父预测。
训练/验证发动机无交集；推理只依赖 NumPy；参数随检查点保存。
我们没有选更激进的 ±20 或全量修正，因为公开 RMSE 更好但 NASA 会反弹。
