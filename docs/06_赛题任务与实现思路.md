## 0. 一句话概括

这个比赛要的**不是一个更准的模型**，而是一个每走一步都会问自己
"我现在还准吗 → 要不要动 → 动什么最划算 → 动坏了能不能退"的系统，
并且把这个过程完整地记录在 SwanLab 上，在断网、限资源、无人值守的条件下跑完。

## 2. 要交什么、怎么被评分

### 2.1 三件套

1. **离线 Docker 镜像**：断网、限资源、无人值守，一条命令跑完全程
2. **SwanLab 云端实验记录**：评委要能点进去看每一步
3. **系统运行说明**：怎么跑、怎么复现

### 2.2 两条评分腿

- **综合性能**：最终模型在漂移数据流上有多准
- **单位增益成本**：`成本 / 性能提升`

```
成本 = α · GPU秒数 + β · 标注条数 + γ · Token数
单位增益成本 = 成本 / max(Δ性能, ε)
```

举个具体例子建立直觉（数字是示意，不是官方公式）：

| 方案 | 最终 MAE | 提升 Δ | 成本 | 单位增益成本 |
|---|---|---|---|---|
| 不动（静态基线） | 0.40 | — | 0 | — |
| 每 20 步重训 | 0.15 | +0.25 | 24 | 96 |
| 一漂移就重训 | 0.11 | +0.29 | 43 | 148 |

**更准的方案反而"更贵"。** 这就是赛题标题里有"超参数优化"的原因：
考的不是"能不能训出好模型"，而是"每一分算力花得值不值"。

我们在 XJTU-SY 代理数据上的真实结果正是这个结构（`docs/05` 第 4 节）：

| 策略 | 平均 MAE | Δ vs 静态 | 总成本 | 单位增益成本 |
|---|---|---|---|---|
| static | 0.407 | — | 6.78 | — |
| periodic | 0.145 | +0.262 | 24.20 | **92.4** |
| trigger | 0.106 | +0.301 | 43.07 | 143.1 |

### 2.3 三条硬门槛（任何一条不过 = 不参与排名）

1. 封闭评测中**无人干预**跑完全部阶段并按时输出；
2. SwanLab 记录**完整**（不能事后编、不能补造）；
3. 性能**不低于静态基线**（部署后永不更新的那个模型）。

> 门槛 3 的含义：宁可不更新，也不能更新完变差。
> 所以"决定不更新"必须是系统里一个**合法、常见、被记录**的动作，不是失败。

## 3. 整体思路：把它写成一个带看门狗的主循环

先不要想"AI 自进化"，用 C++ 的思维写成状态机：

```cpp
Model champion = train(warmup_data);          // 上线时训一次的模型
while (stream.has_next()) {
    Batch b = stream.next();
    Metrics m = evaluate(champion, b);        // 当前表现

    DriftSignal d = monitor.observe(b);       // 1. 漂移了吗
    Diagnosis   g = diagnose(d, m);           // 2. 是什么漂移
    Action      a = policy.decide(g, m, budget);  // 3. 要不要动、动什么

    if (gate.approve(a)) {                    // 4. 门控：预算/白名单/幅度
        Model cand = apply(a);                //    重训 / 调参 / 微调
        if (cand.score >= champion.score - margin)   // 5. 同一份考卷上比
            champion = cand;                  //    晋升
        else
            reject(a);                        //    拒绝，但也要记录
    }

    if (champion.degrading_for(3)) rollback(); // 6. 连续变差就回滚
    audit.log(step, d, g, a, cost);           // 7. 全程留痕
}
```

**这条主循环就是作品本身**，模型只是循环里一个可替换的零件。

### 3.1 分层与代码位置

| 层 | 职责 | 文件 | 状态 |
|---|---|---|---|
| L0 数据/特征 | 原始信号 → 特征缓存 | `src/data/xjtu.py`、`loader.py` | ✅ 36 维、9,216 快照 |
| L1 模型 | 分类 / RUL 回归 | `src/models/baseline.py` | ✅ HGB，CPU 0.1 s/次 |
| L2 监控 | PSI + JS + 残差 | `src/monitor/drift.py` | ✅ |
| L3 策略 | static / periodic / trigger | `src/policy/policies.py` | ✅ |
| L4 闭环 | 晋升 + 回滚 + 成本 | `src/harness/loop.py` | ✅ |
| L5 Harness | LLM 编排 + 工具白名单 | `src/harness/`（待建） | ❌ |
| L6 审计 | 五件套收拢、JSONL 留痕 | `src/audit/`（待建） | ⚠️ 逻辑散落 |

### 3.2 系统内部长什么样

```
                    ┌──────────────────────────────┐
 数据流 ──────────▶ │  监控：PSI / JS / 误差缺口     │
 (带漂移)           └──────────────┬───────────────┘
                                   │ 漂移信号 + 诊断
                                   ▼
                    ┌──────────────────────────────┐
                    │  策略：规则表 / Bandit / LLM   │
                    └──────────────┬───────────────┘
                                   │ 动作（白名单）
                                   ▼
                    ┌──────────────────────────────┐
                    │  门控：基线 / 预算 / 幅度上限   │
                    └──────────────┬───────────────┘
                         批准      │      拒绝
                    ┌─────────────┴──────────┐
                    ▼                        ▼
            挑战者训练（重训/调参/微调）     记录理由，保持现状
                    │
                    ▼
            同一 holdout 上比较 ──赢──▶ 晋升 ──持续变差──▶ 回滚
                    │
                    └──▶ 审计日志 + 成本账本 + SwanLab
```

## 4. "微调"到底指什么（最容易讲混的部分）

小白最容易把下面四件事都叫"微调"，但它们完全不同：

| 做法 | 一句话 | 成本 | 适用 |
|---|---|---|---|
| **从零重训** | 丢掉旧模型，用新数据重新训 | 中 | 表格数据、树模型 |
| **微调 fine-tune** | 保留旧权重，用小学习率再训几轮 | 低 | 神经网络 |
| **增量学习** | 只喂新数据，模型在线更新 | 最低 | 特定算法 |
| **超参优化 HPO** | 结构不变，只换学习率/叶子数/窗口 | 中 | 所有模型 |

生活类比：

- 从零重训 = 把员工开掉重新招一个
- 微调 = 老员工去上三天新课，手艺还在
- 增量学习 = 边干边学
- 调超参 = 人不变，只换工作方法（每天汇报 → 每周汇报）

### 4.1 我们到底该用哪个：先看官方数据长什么样

**情况 A：官方给预提取好的特征表格（概率较大）**

规则写了"数据小、有预提取特征、CPU 可完成基础任务"。

→ 树模型没有梯度，**不存在真正的微调**，只能重训。
我们实测：36 维、240 个样本，重训一次 **0.1 秒**。
这种情况硬做"微调"是自欺欺人，评委一问就穿。

→ 正确做法：把"微调"落到**超参数优化**上——策略层动态更换
`max_iter / learning_rate / max_leaf_nodes / 窗口长度`。
每个配置都是一次"训练实验"，全部进成本账本。
**标题里的"模型训练与超参数优化"考的正是这个。**

**情况 B：官方给原始信号，需要神经网络（如 1D-CNN）**

这时微调才真正划算，标准配方：

```
1. 冻结主干（conv 层不动），只训最后 1~2 层
2. 学习率 1e-4（从零训练通常 1e-3，小 10 倍）
3. 只跑 2~3 个 epoch
4. 按时间顺序切验证集（不能随机切，否则未来数据泄漏）
5. 验证集连续 2 轮不降就早停
6. 微调前后在同一验证集上比，差超过 margin 就拒绝
```

**情况 C：没有标签 / 标签很贵**

连微调都做不了，只能做无监督漂移检测（PSI）+ 少量标注的主动学习。
这也是成本公式里有 β·标注的原因。

### 4.2 微调的三个死亡陷阱

1. **灾难性遗忘**：只拿最近 240 个样本微调，早期规律被覆盖。
   对策：训练窗口别太短，或新旧数据混合。
2. **小窗口过拟合**：240 样本、36 维，树深了必过拟合。
   对策：`min_samples_leaf=20`、`l2_regularization=0.5`、早停。
3. **拿不同分布的验证集比较**：我们真实踩过的坑——
   冠军的 0.05 是在"早期简单数据"上测的，挑战者的 0.15 是在"晚期困难数据"上测的，
   直接比会永远晋升失败。**必须在同一个 holdout 上比。**

### 4.3 微调什么时候该触发（和"重训"的决策表）

| 条件                | 推荐动作          | 理由           |
| ----------------- | ------------- | ------------ |
| 特征漂移、误差上升、模型是树模型  | 重训（小窗口）       | 树模型只能重训      |
| 特征漂移、误差上升、模型是神经网络 | 微调最后几层        | 省算力，收敛快      |
| 只有误差上升、特征没漂       | 先查标签/概念漂移，再调参 | 可能是标签问题，重训无效 |
| 无标签可用             | 不训练，只报警       | 强行更新会违反硬门槛 3 |
| 预算快用完             | 不动作（none）     | 保底比乱动强       |

## 5. RSI 怎么实现（别想玄了）

RSI = Recursive Self-Improvement，"系统改进自己"。拆成两层就很好落地。

### 5.1 第 1 层：模型层自进化（已有）

系统发现模型变差 → 用新数据重训/调参 → 验证 → 替换。
这就是普通的 ML 运维，不难，我们已经跑通。

### 5.2 第 2 层：策略层自进化（加分项，还没做）

系统不只改进模型，还改进**"什么时候该动、动哪个动作"这套规则本身**。

- 现在：`if PSI > 0.25 or 误差 > 0.06 then 重训`，阈值是人拍的
- 自进化：记录"每次触发后实际提升多少、花多少成本"，
  把阈值往"单位增益成本最低"的方向挪；或用多臂老虎机在
  `{不动作, 重训, 调参, 微调}` 里选

一个带成本记账的 bandit 就够，不用高深算法：

```
每个动作维护: 尝试次数 n, 平均收益 r
选择时: score = r + c * sqrt(ln(N) / n)    // 收益高、试得少的优先
执行后: 用真实 perf 变化和真实成本更新 r
```

C++ 类比：一个 `std::map<Action, Stats>` 加一个选择函数，几十行。

### 5.3 第 3 层：LLM Harness（评委要看的东西）

规则表能跑，为什么还要 LLM？因为赛题要求有一个"Harness 层"。
Harness 就是**给 LLM 一套工具，让它来编排**：

```
输入（结构化状态）:
  {"psi_max": 0.41, "error_gap": 0.12, "diagnosis": "covariate",
   "budget_left": 6, "last_action": "retrain", "steps_since": 5}

LLM 输出（必须是 JSON）:
  {"action": "hpo", "params": {"max_iter": 120}, "reason": "..."}
```

代码拿到输出后做三件事：

1. **白名单校验**：`action` 不在枚举里 → 拒绝
2. **幅度上限**：一次只改一个超参，且不超过 ±50%
3. **超时 / 异常 fallback**：3 秒没回、不是合法 JSON → 退回规则策略

这样既满足"LLM 驱动"，又不会因为它胡说八道把系统搞崩。

> 注意规则限制：驱动 Harness 的 LLM 只能是 PyTRiO 训练的模型或 Qwen3.8-27B，
> 且最终镜像**离线**，不能调外部 API。本地权重是否预置在评测机上仍是待确认问题（Q7）。

### 5.4 受控五件套（缺一个都可能被扣分）

| 机制 | 一句话 | 类比 | 现状 |
|---|---|---|---|
| 白名单 | 只允许 4 个动作 | `enum class Action` | 待收拢 |
| 幅度上限 | 一次最多改一个参数、±50% | 限速 | 待实现 |
| 次数上限 | 一条流最多重训 12 次 | 预算 | ✅ `max_retrains` |
| kill-switch | 环境变量一设就停止更新 | `std::atomic<bool> stop` | 待实现 |
| 审计日志 | 每步决策 append-only 落盘 | 黑匣子 | ⚠️ 部分在 metrics.json |

成本账本（`src/eval/cost.py`）已经能记 GPU 秒 / 标注数 / Token，
`metrics.json` 已记录每步滑移、诊断、门控理由。
把两者拼成 JSONL 就是审计日志，缺的只是把它独立成模块并加 kill-switch。

### 5.5 RSI 的边界（答辩必答）

**自我改进 ≠ 随便调参。** 一个合格的 RSI 系统必须能回答：

- 它改了什么？（动作 + 参数 + 理由，全部落盘）
- 为什么允许它改？（白名单 + 门控 + 预算）
- 改坏了怎么办？（回滚 + kill-switch）
- 凭什么说改好了？（同一 holdout 上的对比 + 多流复现）
- 总共花了多少？（成本账本，单位增益成本可算）

答不出这五条，就只是"自动调参脚本"，不是受控自进化。

## 6. 知识点逐个讲（小白版）

**1. 数据漂移**
工厂数据不是静止的：设备磨损、换季、换原料、传感器老化，
都会让"今天的数据"和"训练时的数据"长得不一样。
*比方*：用去年的题库备考，今年题型变了。
*我们*：轴承 RMS 从 0.56 涨到 7.27，这就是真实漂移。

**2. 协变量漂移（covariate shift）**
输入 X 的分布变了，但"X→Y 的规律"没变。
*比方*：换了一批同型号但更旧的设备，读数整体偏高，
但"读数高 = 快坏了"依然成立。

**3. 概念漂移（concept drift）**
规律本身变了，同样的输入对应不同答案。
*比方*：以前"咳嗽 = 感冒"，现在"咳嗽 = 过敏"。
*我们*：合成流里对调类别标签来模拟。

**4. 标签漂移（label shift）**
各类别出现的比例变了（故障样本变多），但每类内部规律没变。

**5. PSI（群体稳定性指数）**
把参考数据和当前数据各切 10 个区间，比较两边占比差异再求和。
*比方*：比较两个班的身高分布直方图，形状差多少。
经验阈值：<0.1 稳定，0.1~0.25 关注，>0.25 显著漂移。
*坑*：样本太少时直方图全是噪声——我们踩过，6 个样本算出来永远是 0。

**6. JS 散度**
衡量两个概率分布差多少，取值 0~1（以 2 为底），0 表示完全一样。
*比方*：PSI 比"输入长相"，JS 比"模型输出习惯"。
模型突然总预测同一个值，JS 会跳起来。

**7. 滚动窗口**
只保留最近 N 步的结果取平均，老数据自动滚出。
*比方*：C++ 的 `std::deque`，固定长度，push 新的挤掉旧的。
窗口越小越灵敏、越抖；越大越稳、越迟钝。

**8. 标签延迟**
预测是现在做的，但真相要过一会儿才知道。
*我们*：`label_lag=1`，当前步只能用上一步及以前的标签训练。

**9. RUL（剩余使用寿命）**
从"现在"到"失效"还剩多久。我们归一化成 0~1：1 = 全新，0 = 已坏。
*比方*：手机电量百分比，只不过预测的是"还能用几次"。

**10. MAE / RMSE**
MAE = 预测误差绝对值的平均，好理解、抗离群；
RMSE 先平方再开方，对大错更敏感。
*我们*：MAE 0.10 表示"平均误差约等于全寿命的 10%"。

**11. 静态基线**
部署时训一次，之后永不更新。它是赛题的及格线，也是所有提升的分母。

**12. 单位增益成本**
`成本 / 性能提升`。提升 0.25 花了 24 成本 → 每提升 0.01 约花 1 个单位。
*关键*：提升越小，这个数越爆炸。所以提升必须真实、够大。

**13. Champion / Challenger**
现任模型（冠军）和候选模型（挑战者）。
挑战者必须在**同一份考卷**上考过冠军才能上位。
*我们踩的坑*：让两人考不同难度的卷子，挑战者永远输。

**14. 门控（Gate）**
更新前的最后一道闸：预算够不够、提升是否显著、动作是否在白名单里。
*比方*：`if (!condition) return;`，只不过拒绝也要记日志。

**15. 回滚（Rollback）**
新模型上线后连续 N 步比上线时还差，就退回上一版。
*比方*：`git revert`，旧版本必须留在内存里随时能切回去。

**16. 超参数优化（HPO）**
模型结构和数据不变，只调"训练配方"：学习率、迭代次数、叶子数、正则强度。
*比方*：菜谱不变，调火候和盐量。
*实现*：小网格 / 随机搜索就够，别上贝叶斯优化——每次试验都要记成本。

**17. Bandit（多臂老虎机）**
在几个动作里反复选，一边试新的（探索），一边用当前最好的（利用）。
*比方*：食堂四个窗口，既想常去最好吃的，又怕错过没试过的。

**18. LLM Harness**
给大模型一套工具（查状态、重训、调参、回滚），
让它输出"下一步做什么"的结构化指令。
*比方*：给实习生一个工具箱和操作手册，但所有工具都有安全锁。

**19. Kill-switch / 审计日志**
一个开关能立刻停止所有自动更新；
一本只能追加不能修改的账，记录谁在什么时候做了什么、依据是什么。
*比方*：急停按钮 + 飞机黑匣子。

**20. 无监督漂移检测**
没有标签时也能发现异常：只看输入分布（PSI）、只看输出分布（JS）、看预测置信度。
*为什么重要*：真实产线 99% 的时间没有标签，等标签来了设备已经坏了。

## 8. 一分钟版（用来在群里解释）

> 比赛给一条会漂移的工业数据流，要求系统自己发现"我不准了"，
> 自己决定要不要更新，更新前先在小验证集上比一比，
> 赢了才上线，上线后连续变差就回滚，每一步都要留记录。
> 评分既看准不准，也看每次提升花了多少算力。
> 我们做的是：监控（PSI/JS）→ 诊断（哪类漂移）→ 策略（动不动）→
> 门控（预算/白名单）→ 训练（重训/调参/微调）→ 对比晋升 → 回滚 → 审计。
> 模型可以换，但这个闭环和留痕不能少。
